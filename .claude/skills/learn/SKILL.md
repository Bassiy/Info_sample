以下の手順で学んだ内容を knowledge/ に保存してください。

knowledge/ はエンジニアとしての第2の頭脳であり、**技術・エンジニアリング概念の知識群**として運用している。
保存前に、今回の内容がその範囲に収まるかを確認する。

**保存してよいもの（例）：** プログラミング・設計パターン・アーキテクチャ・セキュリティ・インフラ・ネットワーク・AI/ML・開発手法・ツール・プロトコル

**保存しないもの（例）：** 政治・経済ニュース・社会情勢・ビジネス戦略・採用トレンド・業界動向など、エンジニアリングに直接関係しないトピック

技術的でないトピックの場合は「これは knowledge/ の対象外です。ニュース・ビジネス情報は sources/ で管理しています。」と伝えて終了する。

## ステップ1: 概念の特定と内容の整理

会話の内容から保存すべき概念を特定する。
`knowledge/concepts/` を確認し、既存ファイルの有無をチェックする。

- **既存ファイルあり** → 現在の内容を読み込み、差分・更新箇所を把握する
- **新規** → 新規作成として扱う

**ソースの引き継ぎ：** 直前に `/deep-dive` または `/study` を実行していた場合、そこで記録された記事URL・書籍情報・取得日付を「ソース」欄に自動で使用する。ユーザーへの確認は不要。

整理した内容をファイルごとに以下の形式でユーザーに提示し、了承を得る：

- 各ファイルの**完成形のMarkdown内容**をコードブロックで表示する
- 新規か更新かを明示する
- 最後に「このまま保存してよいですか？修正があれば教えてください。」と伝える

ユーザーは目視で内容を確認し、修正を指示できる。修正があれば反映してから再提示する。

## ステップ2: concepts/ に保存

ユーザーの了承後、確認なしで即座にファイルを作成・更新する。

以下のフォーマットで `knowledge/concepts/{概念名}.md` を作成または更新する：

```markdown
# 概念名

## 概要
一言で説明する。

## 理解したこと
<!-- 表現の優先順位：比較・対応関係 → テーブル、フロー・構造 → Mermaid図、それ以外 → 箇条書き -->
<!-- 箇条書きは図やテーブルで表現できない場合の最終手段とする -->

## 関連概念
関連する概念名（knowledge/concepts/ 内の他ファイル）

## ソース
- 日付・出典（記事URL、書籍名など）

## タグ
カンマ区切りのキーワード
```

## ステップ3: 構造化の確認

保存が完了したら、以下を確認する：

「図・テーブルで構造化できる箇所はありますか？追加・書き直しがあれば対応します。」

- 比較・対応関係 → テーブル
- フロー・順序・呼び出し関係 → Mermaid図（flowchart / sequenceDiagram / classDiagram）
- 上記で表現できない場合のみ箇条書き

ユーザーが希望すれば対応し、再保存する。不要であれば次のステップへ。

## ステップ4: /connect の提案

構造化が完了したら、以下の一文を添える：

「`/connect` で、この概念と他の概念の繋がりを探してみますか？」

ユーザーが希望すれば `/connect` に引き継ぐ。希望しなければここで終了。
